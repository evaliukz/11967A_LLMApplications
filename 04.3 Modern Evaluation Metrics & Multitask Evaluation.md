# Modern Evaluation Metrics & Multitask Evaluation

## 现代 LLM 评估指标------BERTScore、COMET、多任务评估大白话笔记

## 0. 这一讲在上一讲基础上解决什么问题？

上一讲我们学了：

``` text
Exact Match → 必须完全一样
WER         → 看需要修改多少词
BLEU        → 更偏 Precision，看生成 n-gram 有多少出现在 reference
ROUGE       → 更偏 Recall，看 reference n-gram 有多少被生成结果覆盖
```

它们有一个共同的问题：

> **它们很大程度上在比较"字面上像不像"，而不是"意思像不像"。**

例如：

``` text
Reference:
The weather is cold today.

Generation:
It is freezing today.
```

人类一看就知道：

``` text
cold ≈ freezing
```

两句话表达的核心意思很接近。

但是传统 word-overlap metric 看到的是：

``` text
cold != freezing
weather != it
```

因此可能低估这个 generation。

现代 evaluation 的一个重要方向就是：

``` text
Word / n-gram overlap
        ↓
Semantic similarity
        ↓
Human preference prediction
```

这一讲主要看两个例子：

``` text
BERTScore
COMET
```

然后进一步讨论：

``` text
为什么不能只用一个 task 判断一个现代 LLM？
        ↓
Multitask Evaluation
```

------------------------------------------------------------------------

# 1. 先回到 Construct vs Metric

上一讲最重要的框架仍然适用：

``` text
Construct
= 我真正关心什么？

例如：
Translation Quality
Summary Quality
Semantic Similarity
Helpfulness

        ↓

Operationalization
= 怎么把这个抽象概念变成可计算的东西？

        ↓

Metric
= BLEU / ROUGE / BERTScore / COMET / ...
```

一个 metric 永远只是对 construct 的某种近似。

例如：

``` text
BLEU score 高
```

并不等于：

``` text
Translation 一定很好
```

更准确地说：

> BLEU 用 lexical n-gram overlap 去 operationalize translation quality
> 的某些方面。

BERTScore 和 COMET 则试图做得更接近"人真正关心的意思"。

------------------------------------------------------------------------

# 2. 为什么要 Moving Beyond Word Overlap？

看一个非常简单的例子。

### Reference

``` text
The child is happy.
```

### Model A

``` text
The child is happy.
```

### Model B

``` text
The kid is joyful.
```

Exact Match：

``` text
A = perfect
B = fail
```

BLEU / ROUGE 也会因为：

``` text
child != kid
happy != joyful
```

让 B 丢掉不少分数。

但人类知道：

``` text
child ≈ kid
happy ≈ joyful
```

所以真正的问题是：

> **我们能不能让 metric 也"知道"这些词在语义上接近？**

这就是 BERTScore 的基本出发点。

------------------------------------------------------------------------

# 3. BERTScore：不要只看词一样不一样，看"意思距离"

BERTScore 的核心思想可以大白话理解成：

> **先用 BERT 把每个 token 变成一个带上下文语义的向量，然后比较
> prediction 和 reference 中 token 的向量有多接近。**

流程：

``` text
Reference text
      ↓
BERT
      ↓
Contextual token embeddings
      ↘
       Cosine Similarity
      ↗
Generated text
      ↓
BERT
      ↓
Contextual token embeddings
```

所以它不是只做：

``` text
cold == freezing ?
```

而是问：

``` text
embedding("cold")
和
embedding("freezing")

方向有多接近？
```

------------------------------------------------------------------------

# 4. 什么叫 Token Embedding？

假设 BERT 把词表示成高维向量。

为了方便，我们假装只有 3 维：

``` text
cold     → [0.8, 0.7, 0.1]
freezing → [0.9, 0.8, 0.1]

banana   → [-0.2, 0.1, 0.9]
```

`cold` 和 `freezing` 的向量方向可能很接近。

而：

``` text
cold
banana
```

方向差很多。

真实 BERT embedding 当然是高维向量，但直觉一样：

> **语义或上下文用法相似的 token，其 contextual embeddings
> 往往更相近。**

------------------------------------------------------------------------

# 5. 为什么强调 Contextual Embedding？

BERT 的 embedding 不是简单的：

``` text
bank → 永远一个固定 vector
```

它会考虑上下文。

例如：

``` text
I deposited money in the bank.
```

和：

``` text
We sat on the river bank.
```

两个 `bank` 的含义不同。

BERT 会根据 surrounding context 得到不同的 contextual representation。

所以 BERTScore 比单纯的词表 synonym lookup 更强：

> **它比较的是 context-aware semantic representations。**

------------------------------------------------------------------------

# 6. Cosine Similarity 是什么？

BERTScore 使用 token embeddings 之间的 **cosine similarity**。

不需要害怕公式，直觉就是：

> **两个向量方向有多像？**

可以把它想成两根箭头：

``` text
→
→
```

方向非常接近：

``` text
cosine similarity 高
```

如果：

``` text
→
↑
```

方向差很多：

``` text
similarity 较低
```

所以：

``` text
cold ↔ freezing
→ high cosine similarity

cold ↔ banana
→ low cosine similarity
```

------------------------------------------------------------------------

# 7. BERTScore 怎么比较一句话？

课程给的核心过程：

1.  用 BERT 分别得到 reference 和 generation 的 per-token embeddings。
2.  计算 token embeddings 之间的 pairwise cosine similarity。
3.  用这些 semantic matches 衡量 prediction 与 reference 的相似程度。

例如：

``` text
Reference:
The weather is cold today.

Generation:
It is freezing today.
```

概念上可能出现：

``` text
cold      ↔ freezing   high similarity
today     ↔ today      very high similarity
is        ↔ is         high similarity
```

于是即使：

``` text
cold != freezing
```

BERTScore 仍然可以给 semantic match credit。

------------------------------------------------------------------------

# 8. BERTScore vs BLEU：最重要区别

BLEU 更像：

``` text
"cold" == "freezing" ?

No
→ no lexical match
```

BERTScore 更像：

``` text
embedding(cold)
        ↕
cosine similarity
        ↕
embedding(freezing)

Very similar
→ semantic credit
```

所以可以记：

``` text
BLEU / ROUGE
→ lexical overlap

BERTScore
→ embedding similarity
→ semantic similarity
```

------------------------------------------------------------------------

# 9. 一个更明显的例子

Reference：

``` text
The company reported a large increase in revenue.
```

Generation：

``` text
The firm's sales grew significantly.
```

传统 overlap metric 会看到：

``` text
company != firm
revenue != sales
increase != grew
large != significantly
```

所以 lexical overlap 不高。

但 semantic metric 有机会发现：

``` text
company ≈ firm
revenue ≈ sales
increase ≈ grew
large ≈ significantly
```

于是 BERTScore 更可能反映人类的直觉：

> 两句话表达了非常相近的意思。

------------------------------------------------------------------------

# 10. BERTScore 的优势

课程强调：

### 1. Flexible Matching

允许：

``` text
synonyms
contextually similar words
paraphrases to some extent
```

而不是必须 exact lexical match。

### 2. Better correlation with human judgment

在一些任务（课程特别提到 machine translation）中，研究发现它比传统
word-overlap metrics 更能与 human judgment 对齐。

直觉：

``` text
Human:
"cold" and "freezing" mean similar things.

BERTScore:
their embeddings are similar.

BLEU:
different strings.
```

所以 BERTScore 的 representation 更接近人类语义判断。

------------------------------------------------------------------------

# 11. BERTScore 的局限：依赖 Embedding Model

这是非常重要的一点。

BERTScore 并不是一个完全独立、永恒不变的尺子。

它依赖：

``` text
Which BERT / embedding model?
Which model version?
```

例如：

``` text
BERT-base
BERT-large
不同 checkpoint
```

可能产生不同 embeddings：

``` text
same sentence
→ different embeddings
→ different similarities
→ different BERTScore
```

所以报告结果时需要说明使用的模型版本，保证：

``` text
Reproducibility
```

大白话：

> **如果两个人拿的"尺子"不是同一把尺子，分数不能随便直接比较。**

课程材料还指出，BERTScore 的适用/验证也受 human annotations
可用性的限制；理解时可以把重点放在：**现代 metric
是否真的更接近人类判断，仍然需要 human judgments 来验证。**

------------------------------------------------------------------------

# 12. 从 BERTScore 再向前一步：COMET

BERTScore 的思路仍然是：

``` text
我设计一个 semantic similarity mechanism
        ↓
希望它和 human judgment 接近
```

COMET 更进一步：

> **既然最终想接近 human judgment，为什么不直接用 human annotations
> 训练一个模型来预测 human judgment？**

这就是 COMET 的关键思想。

------------------------------------------------------------------------

# 13. COMET 是什么？

COMET：

> **Cross-lingual Open-source Metric for Evaluating Translations**

课程把它作为一个：

``` text
learned evaluation metric
```

来介绍。

它不是只数 overlap，也不是简单算 embedding similarity。

而是利用：

``` text
Historical Human Annotations
        ↓
Train Evaluation Model
        ↓
Predict Human Ratings / Preferences
```

大白话：

> **以前的 metric 是工程师手工设计评分规则；COMET 更像训练一个"AI
> 阅卷老师"，让它学习人类过去是怎么打分的。**

------------------------------------------------------------------------

# 14. COMET Approach 1：Regression

假设人类 evaluator 对 translation 打分：

``` text
Translation A → 4.8 / 5
Translation B → 3.2 / 5
Translation C → 1.5 / 5
```

这些就是 training labels。

训练：

``` text
Translation / relevant inputs
        ↓
COMET model
        ↓
Predicted human rating
```

例如：

``` text
Model output:
"The weather is freezing today."

COMET prediction:
4.6 / 5
```

这叫 regression，因为输出是连续数值。

------------------------------------------------------------------------

# 15. 什么是 Likert Scale？

课程提到 human ratings，例如 Likert-scale ratings。

简单理解：

``` text
1 = Very Bad
2 = Bad
3 = Okay
4 = Good
5 = Excellent
```

人类先标大量 examples：

``` text
Example 1 → 5
Example 2 → 2
Example 3 → 4
...
```

COMET regression model 学：

``` text
text → human score
```

以后遇到新 output，就自动预测人可能给多少分。

------------------------------------------------------------------------

# 16. COMET Approach 2：Ranking

第二种思路不是问：

> 这句话应该打 4.3 还是 4.5？

而是问：

> **A 和 B，人更喜欢哪个？**

例如：

``` text
Reference / source context
        ↓

Translation A:
The weather is cold today.

Translation B:
Today's weather is banana.

Human preference:
A > B
```

训练模型学习：

``` text
A should rank above B
```

以后：

``` text
Candidate A
Candidate B
      ↓
COMET
      ↓
A > B
```

这就是 ranking / preference learning。

课程指出，ranking approach 在与 human judgments 的 correlation
上表现更强。

------------------------------------------------------------------------

# 17. 为什么 Ranking 可能比 Regression 更自然？

想象让你评价两杯咖啡。

问题 A：

``` text
给这杯咖啡一个 1~5 的精确分数。
```

你可能纠结：

``` text
4.1?
4.3?
4.5?
```

但问题 B：

``` text
A 和 B 哪杯更好喝？
```

很多时候更容易回答。

文本评价也类似。

人类可能不容易稳定地区分：

``` text
4.2 vs 4.4
```

但可能很容易说：

``` text
A is better than B.
```

因此 pairwise preference / ranking 是现代 evaluation 中非常重要的思想。

------------------------------------------------------------------------

# 18. COMET 的优势

最重要：

> **直接利用 human annotations 学习人类 preference。**

可以把演进路线理解成：

``` text
BLEU / ROUGE
→ 手工设计 lexical overlap

BERTScore
→ pretrained embeddings + semantic similarity

COMET
→ learn from human judgments
```

越来越靠近：

``` text
What humans actually prefer
```

------------------------------------------------------------------------

# 19. COMET 的问题：Human Labels 很贵

COMET 的强项也是它的限制。

因为它需要：

``` text
large amount of human annotated data
```

这意味着：

``` text
Recruit evaluators
Train evaluators
Annotate examples
Quality control
```

都需要成本。

如果某个 task：

``` text
有大量高质量 human annotations
```

可以训练不错的 learned metric。

如果：

``` text
几乎没有 human annotations
```

就困难很多。

所以课程强调：

> **它更适用于有较充分 annotated data 的任务。**

------------------------------------------------------------------------

# 20. 三代 Metric 放在一起理解

## 第一代：Lexical Match

``` text
BLEU / ROUGE

Prediction
    ↕
Reference

Do words / n-grams overlap?
```

------------------------------------------------------------------------

## 第二种思路：Semantic Representation

``` text
BERTScore

Prediction → BERT → embeddings
                       ↕ cosine similarity
Reference  → BERT → embeddings

Do they mean similar things?
```

------------------------------------------------------------------------

## Learned Human-Preference Metric

``` text
COMET

Human judgments
      ↓
Train metric model
      ↓
New output
      ↓
Predict human rating / preference
```

一句话：

``` text
BLEU/ROUGE → compare words
BERTScore  → compare semantic embeddings
COMET      → learn to predict human judgments
```

------------------------------------------------------------------------

# 21. 为什么现代 LLM 需要 Multitask Evaluation？

假设有两个学生：

``` text
Student A:
Math = 100
English = 40
History = 30

Student B:
Math = 85
English = 85
History = 85
```

如果只考数学：

``` text
A looks stronger
```

但如果你的 construct 是：

``` text
general academic capability
```

只考数学显然不够。

现代 LLM 也是一样。

------------------------------------------------------------------------

# 22. 一个 LLM 可以做太多事情

现代 general-purpose language model 可能需要：

``` text
Question Answering
Summarization
Translation
Classification
Reasoning
Generation
...
```

如果只跑：

``` text
one summarization benchmark
```

然后说：

``` text
This is a better general-purpose LLM.
```

证据显然太窄。

所以需要：

> **Multitask Evaluation = 在多个不同 task 上测模型。**

------------------------------------------------------------------------

# 23. Multitask Evaluation 的核心目标

大白话：

> **不要只看一个科目，看看这个模型的"综合成绩单"。**

例如：

``` text
Model A

QA               87
Summarization    91
Translation      82
Classification   94
Reasoning        76
```

这样比一个单独 score 更能展示：

``` text
strengths
weaknesses
breadth
```

------------------------------------------------------------------------

# 24. Composite Score 是怎么来的？

有时 benchmark 会把多个 task：

``` text
Task 1 → score
Task 2 → score
Task 3 → score
...
```

组合 / 平均：

``` text
Overall Score
```

例如简化：

``` text
QA            = 90
Translation   = 80
Summarization = 85

Average = 85
```

但需要小心：

> **一个 overall number 会隐藏不同 task 的差异。**

例如：

``` text
Model A:
Math 100
Writing 50

Average 75

Model B:
Math 75
Writing 75

Average 75
```

同样：

``` text
Overall = 75
```

能力结构却完全不同。

所以实际看 benchmark 时，最好同时看：

``` text
overall score
+
per-task breakdown
```

# 25. Benchmark 例子 1：GLUE

课程介绍：

> GLUE 最初是一个 NLP benchmark suite，主要包含 classification-style
> tasks，例如 sentiment analysis。

它的思想是：

``` text
不是测一个 dataset
而是测一组 NLP tasks
```

然后：

``` text
GLUE
  ↓
多个任务
  ↓
综合判断模型 language understanding 能力
```

之后出现：

``` text
SuperGLUE
```

用来支持更复杂、更有挑战性的 NLP evaluation。

最重要的不是背 GLUE 具体有哪些 task，而是理解：

> **Benchmark suite = 一套考试，而不是一道题。**

# 26. Benchmark 例子 2：GEM

GEM 主要关注：


课程特别强调它是一个 dynamic benchmark：

``` text
tasks evolve / update over time
```

为什么重要？

因为 language generation 变化很快。

以前重要的 generation task 和今天关心的能力可能不同。

所以 GEM 的思想是：

> **Evaluation 本身也应该随着 field 和用户需求变化。**

这和后面的：

``` text
Iterative Improvement
```

直接相关。

# 27. Benchmark 例子 3：XTREME

课程介绍 XTREME 时强调：

``` text
large collection of evaluation tasks

```

并强调 benchmark 应覆盖更广泛的能力和领域，而不只是一个狭窄 NLP task。

``` text
        ↓

```

------------------------------------------------------------------------

# 28. 为什么 Multitask Evaluation 很重要？

### 原因 1：模型能力不是一维的

``` text
Good at translation
```

不等于：

``` text
Good at QA
Good at summarization
Good at reasoning
```

------------------------------------------------------------------------

### 原因 2：避免对一个 benchmark 过度优化

如果所有人都只看一个考试：

``` text
Benchmark X
```

开发就可能越来越针对：

``` text
How do we maximize X?
```

但：

``` text
X score ↑
```

不一定意味着：

``` text
Real-world usefulness ↑
```

------------------------------------------------------------------------

### 原因 3：更接近 general-purpose LLM 的真实使用方式

用户不会只让模型：

``` text
do sentiment classification
```

而可能今天：

``` text
summarize document
```

明天：

``` text
answer question
```

后天：

``` text
translate text
```

所以 evaluation 也应该覆盖 diverse tasks。

------------------------------------------------------------------------

# 29. Automatic Metrics 仍然不是最终答案

课程最后非常重要的一点：

> **Automatic evaluation should be complemented by human evaluation and
> broader societal considerations.**

也就是说：

``` text
Automatic Metric
≠
Complete Evaluation
```

为什么？

因为 metric 永远是在 operationalize 某个 construct。

有些东西很难完全压缩成一个数字：

``` text
Helpfulness
Fairness
Social impact
Appropriateness
Human preference
Real-world utility
```

------------------------------------------------------------------------

# 30. 问题 1：Metric Implementation 可能不一致

即使大家说：

``` text
"We use the same metric."
```

具体 implementation 可能不同。

例如：

``` text
Tokenization?
Normalization?
Model checkpoint?
Preprocessing?
Dataset version?
```

不同选择可能导致不同 score。

BERTScore 尤其明显：

``` text
Which embedding model?
Which version?
```

所以 reproducibility 非常重要。

------------------------------------------------------------------------

# 31. 问题 2：Benchmark 可能会过时

课程提到 stationarity / benchmark aging 的问题。

假设 benchmark 是：

``` text
2018 年的数据
```

但模型训练于：

``` text
2026
```

世界、语言、数据 distribution 都可能变化。

甚至 benchmark 数据可能进入训练 corpus。

于是：

``` text
Benchmark score
```

不一定继续代表：

``` text
Current real-world performance
```

所以 evaluation 不能"一套 benchmark 用十年不变"。

------------------------------------------------------------------------

# 32. 为什么 Evaluation 需要 Iterative Improvement？

模型不断进步：

``` text
Model capability ↑
```

旧 metric 可能不再能区分模型。

例如：

``` text
Model A = 98%
Model B = 98.5%
Model C = 99%
```

benchmark 接近 saturation。

或者我们发现：

``` text
Metric ↑
Human preference ↛ ↑
```

说明 metric 与 construct 的 alignment 不够好。

于是需要：

``` text
Re-examine construct
        ↓
Improve metric
        ↓
Update benchmark
        ↓
Validate against humans
        ↓
Repeat
```

所以：

> **Evaluation 本身也是一个不断迭代的 research problem。**

------------------------------------------------------------------------

# 33. 把整个课程串起来

到这里，你已经可以把 automatic evaluation 的演进理解成：

``` text
Exact Match
│
│ 太严格
↓
WER
│
│ 看 edit distance，但不懂 semantics
↓
BLEU / ROUGE
│
│ 看 n-gram overlap，但 synonyms 会被误伤
↓
BERTScore
│
│ 用 contextual embeddings 捕捉 semantic similarity
↓
COMET
│
│ 从 human annotations 学 human preference
↓
Multitask Evaluation
│
│ 单个 task 仍然不足以描述 general-purpose LLM
↓
Human + Societal Evaluation
```

注意这不是说后面的 metric 简单"取代"前面的 metric。

更准确：

> **不同 metric operationalize 不同 constructs，各有适用场景。**

------------------------------------------------------------------------

# 34. 用一个 Translation 例子贯穿所有 Metric

Reference：

``` text
The weather is cold today.
```

Generation：

``` text
It is freezing today.
```

### Exact Match

``` text
0
```

因为字符串不同。

### BLEU

有一些 word / n-gram overlap：

``` text
is
today
```

但：

``` text
cold != freezing
```

所以 semantic equivalence 没有被充分捕捉。

### ROUGE

也会发现 reference 的一部分内容被覆盖，但同样依赖 lexical overlap。

### BERTScore

看到：

``` text
cold ↔ freezing
```

contextual embeddings 相似。

因此给 semantic similarity credit。

### COMET

如果 human annotation 数据中，人们普遍认为这种翻译很好：

``` text
Human preference
        ↓
training
        ↓
COMET learns this pattern
```

于是 metric 可以尝试直接预测：

``` text
Humans would rate/prefer this translation highly.
```

这就是 modern evaluation 的发展方向。

------------------------------------------------------------------------

# 35. 最重要的面试问题

## Q1. Why do we need modern metrics beyond BLEU and ROUGE?

> **BLEU and ROUGE rely heavily on lexical overlap and can penalize
> semantically equivalent paraphrases. Modern metrics such as BERTScore
> use contextual embeddings to capture semantic similarity and can
> better align with human judgments in some tasks.**

------------------------------------------------------------------------

## Q2. How does BERTScore work?

> **BERTScore generates contextual token embeddings for the reference
> and prediction using a pretrained BERT-like model, then uses pairwise
> cosine similarity to identify semantically similar tokens.**

------------------------------------------------------------------------

## Q3. What is the main advantage of BERTScore over BLEU?

> **BERTScore can reward semantically similar words and paraphrases even
> when they do not have exact lexical overlap.**

------------------------------------------------------------------------

## Q4. What is a limitation of BERTScore?

> **The score depends on the pretrained embedding model and model
> version used, so these details must be reported for reproducibility.
> Its alignment with the target construct also needs to be validated
> against human judgments.**

------------------------------------------------------------------------

## Q5. What is COMET?

> **COMET is a learned evaluation metric for machine translation that
> uses human-annotated data to train models to predict human ratings or
> preferences.**

------------------------------------------------------------------------

## Q6. Regression vs Ranking in COMET?

``` text
Regression:
"What score would a human give?"
→ predict 1–5 / continuous rating

Ranking:
"Which output would humans prefer?"
→ A > B
```

课程指出 ranking approach 与 human judgments 的 correlation 更强。

------------------------------------------------------------------------

## Q7. Why is multitask evaluation important?

> **Modern language models are general-purpose systems with capabilities
> across many tasks. Evaluating only one task can provide a narrow or
> misleading picture, while multitask benchmarks reveal strengths and
> weaknesses across diverse capabilities.**

# 37. 超短 Cheat Sheet

``` text
TRADITIONAL
BLEU / ROUGE
→ word / n-gram overlap
→ 不真正理解 synonym / paraphrase

BERTScore
→ BERT contextual embeddings
→ pairwise cosine similarity
→ semantic similarity
→ "cold" ≈ "freezing"
→ specify embedding model/version

COMET
→ learned evaluation metric
→ trained from human annotations

COMET Regression
→ predict human score

COMET Ranking
→ predict human preference
→ A > B

MULTITASK EVALUATION
→ 一个 LLM ≠ 一种能力
→ test many tasks
→ holistic capability profile

Examples:
GLUE / SuperGLUE
GEM
XTREME

AUTOMATIC METRIC ≠ COMPLETE EVALUATION
→ supplement with human evaluation
→ consider broader social context
→ benchmarks can age
→ metrics must evolve
```

# 38. 最后一句话记住整讲

> **现代 NLP evaluation
> 正在从"两个答案用了多少相同的词"，发展到"它们表达的意思是否相似"，再进一步到"人类会如何评价或偏好这些答案"；而对于
> general-purpose LLM，仅有一个 metric 或一个 task 都不足够，因此需要
> multitask benchmarks，并结合 human evaluation
> 来判断模型是否真正符合实际应用中的目标。**
