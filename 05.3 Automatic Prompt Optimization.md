# 5.5 --- Automatic Prompt Optimization

> **一句话主线：** Prompt 对模型表现影响很大，但靠人手工调 prompt
> 又慢、又不稳定，所以可以把 **prompt 本身当成一个需要 optimization
> 的对象**，让算法或 LLM 自动地 `生成 → 测试 → 改进 → 再测试`。

------------------------------------------------------------------------

# 1. 为什么要 Automatic Prompt Optimization？

上一节讲过 In-Context Learning：

``` text
Model weights 不变
        ↓
改变 prompt
        ↓
模型表现可能发生很大变化
```

这既是 ICL 的优点，也是它的麻烦。

课程给出三个主要原因。

### 1.1 手工写 Prompt 是 Trial-and-Error

现实中的 prompt engineering 很像：

``` text
Prompt v1
→ 测一下
→ 不太好

Prompt v2
→ 换个 wording
→ 再测

Prompt v3
→ 加 instruction
→ 再测

Prompt v4 ...
```

也就是不断：

``` text
write → evaluate → rewrite → evaluate
```

需要大量人工 effort 和 expertise。

### 1.2 LLM 对 Prompt 可能 Unpredictably Sensitive

两个意思几乎一样的 prompts：

``` text
Classify whether this review is positive or negative.
```

和：

``` text
Determine the sentiment of this review.
```

在人看来几乎是一回事，但模型表现可能明显不同。

所以：

> **Prompt quality 很难只靠人的直觉预测。**

### 1.3 Prompt 不一定 Portable

一个 prompt 在：

``` text
Model A
```

上调得很好，换成：

``` text
Model B
```

可能效果下降。

而且 model、task、prompt tricks 都一直在变化。

因此产生一个自然想法：

> **既然 prompt 是影响 performance 的重要变量，为什么不直接 optimize
> prompt？**

------------------------------------------------------------------------

# 2. 核心思想：Prompt as an Optimizable Artifact

传统 optimization：

``` text
Model parameters θ
→ optimize θ
```

Prompt optimization：

``` text
Prompt P
→ evaluate P
→ modify P
→ find better P
```

大白话：

> **以前我们训练模型参数；现在模型可以完全不动，把 prompt
> 当成"参数"一样搜索。**

注意，这里"参数"是类比。Hard prompt 本身仍然是 text/token sequence，不是
model weights。

------------------------------------------------------------------------

# 3. Hard Prompt vs Soft Prompt

这是本节非常重要的区别。

## Hard / Discrete Prompt

就是我们正常能读懂的文字：

``` text
Classify the sentiment of the following review.
Return only Positive or Negative.
```

优化对象：

> **actual tokens of the prompt text**

例如算法尝试：

``` text
Prompt A:
Classify the sentiment...

Prompt B:
Determine whether the following review...

Prompt C:
Read the review and return...
```

本质是：

``` text
在 discrete text/token space 中搜索
```

------------------------------------------------------------------------

## Soft / Continuous Prompt

Soft prompt 不一定对应任何人类词语。

模型真正处理的 token 会先变成 embeddings：

``` text
token → embedding vector
```

Soft prompt 的想法是：

``` text
不要寻找最好的文字
        ↓
直接学习一组 vectors
        ↓
把这些 vectors prepend 到 input embeddings 前面
```

例如概念上：

``` text
[v1] [v2] [v3] [v4] + embeddings(input)
```

其中：

``` text
v1, v2, v3, v4
```

是 trainable continuous vectors。

它们可能根本无法翻译成：

``` text
"Please classify sentiment..."
```

这样的自然语言。

------------------------------------------------------------------------

# 4. Hard vs Soft Prompt 对比

                     Hard / Discrete Prompt           Soft / Continuous Prompt
  ------------------ -------------------------------- ---------------------------
  优化什么           Actual prompt tokens             Continuous vectors
  怎么优化           Search / edits / LLM rewriting   Gradient descent
  Model access       常可使用 black-box API           通常需要 white-box access
  Interpretability   通常是 readable text             vectors 没有对应文字
  Portability        string 可复制到其他 model/API    tied to tuned model

课程 slide 还指出，soft prompt tuning 只训练很小比例的
parameters，并且随着 model scale 增大，可以接近 full fine-tuning
performance。

------------------------------------------------------------------------

# 5. Black-Box vs White-Box

理解 hard/soft prompt 时，这两个词很重要。

### Black-box

你只能：

``` text
send prompt → get response
```

看不到内部：

-   embeddings
-   gradients
-   weights

很多 commercial LLM API 都可以从这种视角理解。

Hard prompt optimization
很适合这种情况，因为只需要修改文字，再调用模型测试。

### White-box

你能访问：

``` text
model internals
+ embeddings
+ gradients
```

Soft prompt optimization 需要 gradient descent，因此通常要求这种更深的
model access。

所以：

``` text
Hard prompt
→ often black-box friendly

Soft prompt
→ usually white-box
```

------------------------------------------------------------------------

# 6. AutoPrompt：Gradient-Guided Discrete Search

这个方法有点反直觉：

> **最终找到的是 discrete tokens，但搜索过程中使用 gradient
> information。**

课程中的 template 类似：

``` text
{sentence} [T] [T] [T] [T] [T] [MASK].
```

这里 `[T]` 是要自动寻找的 **trigger tokens**。

最终可能找到：

``` text
{sentence} atmosphere alot dialogue Clone totally [MASK].
```

人看到会觉得：

> "这是什么鬼句子？"

但它可能让 model 在 SST-2 sentiment classification 上表现很好。

------------------------------------------------------------------------

# 7. Trigger Tokens 是什么？

大白话：

> **算法自动找到的一组 token，把它们放到每个 input
> 附近，可以让模型更容易完成目标 task。**

概念：

``` text
Input sentence
+
shared trigger tokens
+
[MASK]
→ masked LM predicts label
```

这些 trigger tokens 对所有 examples 共用。

AutoPrompt 使用 gradient information 来指导：

> "哪些 vocabulary tokens 替换进去可能让 task objective 更好？"

最终仍然选择真实 vocabulary tokens，所以它属于：

> **gradient-guided discrete search**

------------------------------------------------------------------------

# 8. AutoPrompt 最重要的 Lesson

课程展示 SST-2 accuracy：

  Model       Manual   Auto   Finetuned
  --------- -------- ------ -----------
  BERT          63.2   82.3        93.5
  RoBERTa       85.2   91.4        96.7

重点不是死背数字，而是：

> **不修改 model weights，仅仅自动寻找 prompt tokens，就可能显著缩小与
> full fine-tuning 的 performance gap。**

但代价是：

``` text
best prompt
= "atmosphere alot dialogue Clone totally ..."
```

完全不自然。

所以课程强调：

> **The winning triggers are not interpretable.**

这揭示一个 trade-off：

``` text
performance ↑
不一定意味着
human readability ↑
```

------------------------------------------------------------------------

# 9. Prompt Optimization 的通用 Loop

这是整节最值得背下来的流程：

``` text
SEED
  ↓
EVALUATE
  ↓
GENERATE
  ↓
FILTER
  ↓
ITERATE
  ↺
```

完整五步：

### Step 1 --- Seed Prompts

先有初始 prompt：

``` text
manual instruction
```

或者让 LLM 根据 demonstrations 自动产生 instruction。

### Step 2 --- Evaluate and Collect Feedback

把 prompt 跑在 validation data 上。

Feedback 可以是：

``` text
numeric score
LLM critique
human feedback
```

### Step 3 --- Generate Candidates

根据 feedback 生成新的 prompt candidates：

``` text
P1
P2
P3
P4
...
```

### Step 4 --- Filter and Retain

因为 evaluation 很贵，不可能无限测试。

所以保留：

``` text
most promising candidates
```

淘汰差的。

### Step 5 --- Iterate

继续：

``` text
evaluate
→ feedback
→ rewrite
→ select
→ repeat
```

直到：

``` text
fixed number of iterations
```

或者：

``` text
improvement stalls
```

------------------------------------------------------------------------

# 10. 最重要的统一框架

课程指出，很多 published prompt optimization methods
表面上差异很大，但底层 skeleton 很相似：

``` text
Seed
→ Evaluate
→ Generate
→ Filter
→ Iterate
```

真正不同的主要是：

``` text
How do we generate candidates?
How do we evaluate candidates?
What feedback signal do we use?
```

这是理解整个领域最有用的抽象。

------------------------------------------------------------------------

# 11. ProTeGi：用 LLM 给 Prompt 写"改卷意见"

ProTeGi 是非常直观的方法。

假设 seed prompt：

``` text
Detect if the message is a jailbreak attack,
i.e. an attempt by a user to break through an AI system's protections.
```

跑 validation examples 后发现有 errors。

例如某个 subtle jailbreak 被误判。

### Step 1：Collect Errors

``` text
Current prompt
→ minibatch
→ predictions
→ find mistakes
```

### Step 2：让 LLM Critique Prompt

把错误交给另一个 LLM：

``` text
Here is the prompt.
Here are the mistakes.
Why is this prompt causing these errors?
```

LLM 可能指出：

``` text
The prompt assumes jailbreak attempts explicitly mention
breaking AI protections, but real attacks can be subtle or indirect.
```

课程把这种 natural-language critique 形象地叫：

> **textual "gradient"**

------------------------------------------------------------------------

# 12. 为什么叫 Textual Gradient？

真正 gradient descent：

``` text
loss
→ gradient tells parameters which direction to move
→ update weights
```

ProTeGi：

``` text
errors
→ LLM critique tells prompt what is wrong
→ rewrite prompt
```

所以可以类比：

``` text
Numerical gradient:
“parameter 应该往这个方向改”

Textual gradient:
“prompt 的问题在这里，应该这样改”
```

它不是真正的 calculus gradient，而是自然语言形式的 optimization
feedback。

------------------------------------------------------------------------

# 13. ProTeGi：Rewrite Prompt

根据 critique，再让 LLM 修改 prompt。

例如：

``` text
Old:
Detect explicit attempts to break AI protections.

Critique:
This misses subtle and indirect attacks.

New:
Classify whether the message attempts to bypass an AI
system's defenses, regardless of how subtle or indirect.
```

于是：

``` text
Error
→ Critique
→ Rewrite
→ New candidate
→ Evaluate
```

还可以通过 paraphrasing 产生附近的更多 candidates，进行 local
exploration。

------------------------------------------------------------------------

# 14. ProTeGi 的结果说明什么？

课程 slide：

> improved the seed prompt by up to **31%** across four classification
> tasks.

同时观察到 optimizer 会把：

``` text
vague task descriptions
```

逐渐改写成：

``` text
precise instructions
```

真正重要的 lesson：

> **Prompt optimization 可以系统性地发现比人工 seed prompt 更有效的
> instruction wording。**

但曲线也显示 performance 不一定每一步都持续增加。

所以：

``` text
more optimization steps
≠ guaranteed monotonic improvement
```

这和后面的 dev-set overfitting 有关系。

------------------------------------------------------------------------

# 15. Prompt Optimization Methods

课程把方法分成几个 families。

### Heuristic Edits

通过：

-   word/phrase edits
-   genetic mutation/crossover
-   Monte Carlo paraphrasing

搜索 better prompts。

Examples：

``` text
GrIPS
EvoPrompt
PromptBreeder
```

### LLM Feedback and Rewriting

``` text
current prompt
→ LLM critique
→ LLM rewrite
```

Examples：

``` text
ProTeGi
PromptAgent
CRISPO
```

### Metaprompt Optimizers

把以前的：

``` text
(prompt, score)
```

pairs 给 LLM，让 LLM 根据历史表现提出更好的 prompt。

Examples：

``` text
OPRO
PE2
```

大白话：

> **把 LLM 自己当 optimizer。**

### Auxiliary Trained Networks

训练额外系统来帮助 prompt optimization，例如：

-   RL policies
-   finetuned rewriter models
-   adversarial setups

Examples：

``` text
RLPrompt
BPO
Tempera
```

### Coverage and Ensembles

不是只寻找一个 universal prompt，而可能：

``` text
different input regions
→ different expert prompts
```

或者组合多个 prompts。

Examples：

``` text
MoP
PromptBoosting
```

### Program Synthesis

优化的不只是一个 prompt，而是整个 multi-stage LLM pipeline 的：

``` text
instructions
+ demonstrations
+ components
```

Examples：

``` text
DSPy
MIPRO
```

------------------------------------------------------------------------

# 16. Feedback Signals：怎么知道 Prompt 好不好？

Optimization 必须有 objective。

课程给三类 feedback。

## 16.1 Numeric Scores

例如：

``` text
Accuracy
F1
Output log-likelihood
Entropy
Learned reward model score
```

优点：

``` text
容易比较
容易排序
容易自动 selection
```

例如：

``` text
Prompt A: F1 = 0.81
Prompt B: F1 = 0.87
Prompt C: F1 = 0.83

→ retain B
```

------------------------------------------------------------------------

## 16.2 LLM Feedback

让 LLM 给自然语言 critique：

``` text
"This instruction is ambiguous about..."
"The prompt fails when..."
"You should explicitly specify..."
```

比单个 number 信息丰富。

例如：

``` text
Score = 0.71
```

只告诉你：

> 不够好。

而 critique 可以告诉你：

> **为什么不好，以及应该怎么改。**

代价：

``` text
每次 critique
→ additional LLM call
→ $$$ + latency
```

------------------------------------------------------------------------

## 16.3 Human Feedback

人类可以：

``` text
compare preferences
```

或者明确告诉系统：

``` text
what the user actually wants
```

优点是更贴近真实需求，但通常：

``` text
slow
+ expensive
+ hard to scale
```

------------------------------------------------------------------------

# 17. 一个很实用的组合

课程给出的 practical recipe：

> **numeric scores for selection, LLM critiques for generation**

大白话：

``` text
谁更好？
→ 用数字 score 判断

为什么不好、下一版怎么改？
→ 让 LLM critique
```

所以：

``` text
Numeric score
→ SELECT

LLM feedback
→ GENERATE / REWRITE
```

这是很值得记住的 system design pattern。

------------------------------------------------------------------------

# 18. Prompt Optimization 的 Gains

课程总结的主要优点：

### 1. 不改 Model Weights 也能大幅提升

``` text
model stays frozen
→ prompt improves
→ task performance improves
```

### 2. 可以通过 Black-Box APIs 工作

很多 hard-prompt methods 不需要：

``` text
weights
gradients
embeddings
```

只需要：

``` text
API(prompt) → output
```

### 3. Systematic and Repeatable

相比：

``` text
“我感觉这个 wording 比较好”
```

automatic optimization 更像：

``` text
objective
→ evaluation
→ candidate generation
→ selection
```

### 4. 最终 Artifact 可以只是一个 String

Hard prompt 最终可能就是：

``` text
"Classify whether..."
```

因此容易：

``` text
inspect
version
store
deploy
rollback
```

------------------------------------------------------------------------

# 19. Prompt Optimization 的 Costs / Risks

## 19.1 需要 Validation Data 和 Trustworthy Metric

如果没有办法判断：

``` text
Prompt A 到底比 Prompt B 好在哪里？
```

就无法 optimize。

因此通常需要：

``` text
labeled validation data
+
reliable metric
```

------------------------------------------------------------------------

## 19.2 很多 LLM Calls

假设：

``` text
100 prompt candidates
×
500 validation examples
```

就可能需要大量 inference。

所以课程强调：

> **evaluation dominates the budget**

Candidate generation 可能不贵，真正贵的是：

``` text
每个 candidate 都要认真测试
```

------------------------------------------------------------------------

## 19.3 Dev-Set Overfitting

这是特别重要的风险。

假设不断在同一 validation set 上：

``` text
generate
→ evaluate
→ modify
→ evaluate
→ modify
→ evaluate
```

最终可能找到：

> **特别适合这 500 个 validation examples 的 prompt**

但到了真正 unseen test data：

``` text
performance ↓
```

这和训练 model overfit training data 很像。

只不过这里变成：

``` text
Model overfitting:
weights overfit training data

Prompt optimization overfitting:
prompt overfits development/validation data
```

所以需要独立 test set 来检查 generalization。

------------------------------------------------------------------------

## 19.4 Prompt 可能变得不可读

AutoPrompt 就展示了：

``` text
atmosphere alot dialogue Clone totally
```

performance 很好，但人完全看不懂。

因此 token-level optimization 有：

``` text
performance
vs.
interpretability
```

trade-off。

------------------------------------------------------------------------

# 20. Automatic Prompt Optimization 和 PEFT 的关系

课程最后给了一个很好的统一视角：

> **Prompt optimization and PEFT are neighbors on a spectrum of model
> adaptation, ordered by how much access to the model you require.**

可以画成：

``` text
Less model access
──────────────────────────────────────→ More model access

Hard Prompt Optimization
        ↓
Soft Prompt Tuning
        ↓
PEFT / LoRA / Adapters
        ↓
Full Fine-Tuning
```

大致理解：

### Hard Prompt Optimization

``` text
Model weights: frozen
Need gradients: often no
Need API only: often yes
Optimize: text
```

### Soft Prompt

``` text
Model weights: mostly frozen
Need gradients: yes
Optimize: prompt vectors
```

### PEFT

``` text
Base model mostly frozen
Train small number of parameters
```

### Full Fine-Tuning

``` text
Update all / most model parameters
```

所以它们不是完全孤立的技术，而是：

> **"为了让模型适应我的 task，我愿意改多少东西、需要多少 model
> access？"**

------------------------------------------------------------------------

# 21. Hard Prompt vs Soft Prompt vs PEFT vs Full Fine-Tuning

  ---------------------------------------------------------------------------------
  Method         Optimize           Update base        Gradient? Interpretability
                 什么？                weights?                  
  -------------- ------------- ---------------- ---------------- ------------------
  Hard Prompt    Text/tokens                 No         Often no High-ish
  Optimization                                                   

  Soft Prompt    Continuous                  No              Yes Low
  Tuning         prompt                                          
                 vectors                                         

  PEFT           Small                Mostly no              Yes Low
                 trainable                                       
                 parameters                                      

  Full           Model                      Yes              Yes N/A
  Fine-Tuning    parameters                                      
  ---------------------------------------------------------------------------------

最核心区别：

``` text
Hard Prompt:
search over TEXT

Soft Prompt:
gradient descent over VECTORS

PEFT:
train a SMALL subset/addition of parameters

Full Fine-Tuning:
train the MODEL parameters broadly
```

# 24. AutoPrompt vs ProTeGi：最容易考的区别

## AutoPrompt

``` text
gradient information
        ↓
search vocabulary
        ↓
find discrete trigger tokens
        ↓
possibly weird/uninterpretable prompt
```

关键词：

> **Gradient-guided discrete search**

## ProTeGi

``` text
run prompt
↓
collect errors
↓
LLM writes natural-language critique
↓
"textual gradient"
↓
LLM rewrites prompt
```

关键词：

> **LLM feedback + natural-language rewriting**

一句话区分：

> **AutoPrompt 用 gradient 帮忙找 token；ProTeGi 用 LLM critique 帮忙改
> instruction。**

# 26. 最终大白话总结

如果这一节只记 **6 句话**：

1.  **Prompt 对 LLM performance 影响很大，但手工 prompt engineering
    是昂贵的 trial-and-error。**
2.  **Automatic Prompt Optimization 把 prompt 本身当成 optimization
    target。**
3.  **Hard prompt 优化的是离散 text/tokens；Soft prompt 优化的是
    continuous vectors。**
4.  **大多数方法都可以抽象成：Seed → Evaluate → Generate → Filter →
    Iterate。**
5.  **AutoPrompt 用 gradient-guided discrete search 找 trigger
    tokens；ProTeGi 用 LLM critique 形成"textual gradient"，再自动
    rewrite prompt。**
6.  **Prompt optimization 不需要修改整个 model，但仍然有 evaluation
    cost、dev-set overfitting 和 interpretability 等问题。**

最终脑内图：

``` text
                Adapt a model to my task
                          │
          ┌───────────────┴────────────────┐
          │                                │
   Don't change model                Change parameters
          │                                │
   Optimize prompt                  PEFT / Fine-tuning
          │
    ┌─────┴─────┐
    │           │
 Hard Prompt  Soft Prompt
    │           │
   text       vectors
    │           │
 discrete    gradient
 search      descent
    │           │
    └─────┬─────┘
          ↓
 Better task performance
```

> **Core takeaway:** Once we realize that prompt wording is a major
> determinant of LLM behavior, prompt design itself becomes an
> optimization problem rather than merely a manual writing skill.
