# Automatic Evaluation in NLP / LLMs

## 1. Automatic Evaluation 到底是什么？

这一讲最核心的问题：

> **有两个 system A 和 B，怎么判断哪个在某个任务上做得更好？**

课程强调用 **system** 而不只是 **model**，因为现实 AI 产品往往是：

``` text
User Question → Retriever → LLM → Post-processing → Final Answer
```

所以 evaluation 既可以评价整个系统，也可以评价其中一个 component。

**Automatic evaluation** 大白话就是：

> **不用每次找人打分，而是用程序、规则或 metric 自动评价系统输出。**

例如数学题：

``` text
Question: 2 + 3 = ?
Gold answer: 5

Model A: 5 → Correct
Model B: 6 → Incorrect
```

程序直接比较 prediction 和 gold answer，就完成了 automatic evaluation。

------------------------------------------------------------------------

## 2. 两个最重要的概念：Construct 和 Measurement

整个 evaluation 可以记成：

``` text
Construct
   ↓
Operationalization
   ↓
Metric / Measurement
   ↓
Score
```

### Construct：我到底想测什么？

Construct 是一个想衡量的抽象属性，例如：

-   correctness
-   generated text quality
-   informativeness
-   toxicity
-   interestingness
-   helpfulness

例如：

``` text
Construct = Summary Quality
```

但 "quality" 本身没有天然公式。

所以：

> **Construct = 我真正关心的东西。**

### Operationalization：这个抽象东西具体怎么测？

例如我们关心：

``` text
Construct:
Answer Correctness

        ↓ operationalize

Metric:
Exact Match Accuracy

        ↓

Score:
0.87
```

或者：

``` text
Construct:
Toxicity

        ↓

Automatic toxicity classifier

        ↓

Score:
0.03
```

所以 **operationalization** 就是：

> **把抽象 construct 变成实际可测量的方法。**

非常重要：

> **Metric 不等于 Construct。**

例如 ROUGE 可以用来近似 summary quality 的某些方面，但：

``` text
ROUGE ≠ Summary Quality
```

------------------------------------------------------------------------

## 3. 一个好的 Metric 应该是什么样？

理想情况下，我们希望 metric 与 construct 有 **monotonic relationship**。

大白话：

> **Metric 越好，我们真正关心的 quality 也应该越好。**

``` text
Metric:
0.5 → 0.6 → 0.7 → 0.8

希望对应：

Actual Quality:
差 → 一般 → 好 → 更好
```

如果 metric 上升，但人类认为结果反而更差，那么这个 metric 就没有很好地
operationalize construct。

------------------------------------------------------------------------

## 4. Human Judgment 的角色

很多 construct 人类可以直觉理解。

例如：

``` text
A: Paris is the capital of France.
B: Banana airplane France purple.
```

人很容易判断 A 更合理。

因此 automatic metric 经常是在尝试：

``` text
Automatic Metric
      ↓
approximate
      ↓
Human Judgment
```

但 human evaluation 也不是永远完美。

例如：

``` text
Is this story interesting?
Is this answer sufficiently informative?
```

不同 evaluator 可能不同意。

因此有时连 construct 本身都存在 ambiguity。

------------------------------------------------------------------------

# 5. Intrinsic vs. Extrinsic Evaluation

最简单的记法：

``` text
Intrinsic
= 看某个 component 好不好

Extrinsic
= 看整个系统最终有没有用
```

------------------------------------------------------------------------

## 6. 用 RAG 举例

假设：

``` text
User Question
      ↓
Retriever
      ↓
Relevant Documents
      ↓
LLM
      ↓
Generated Answer
      ↓
User
```

### Extrinsic Evaluation

问：

> **整个 RAG system 最终有没有帮助用户完成任务？**

例如：

``` text
Without RAG:
20 minutes / 70% accuracy

With RAG:
8 minutes / 92% accuracy
```

这是在评价 **end-to-end utility**。

> **Extrinsic = evaluate the whole process / final task.**

### Intrinsic Evaluation

只评价 Retriever：

``` text
Question → Retriever → Did it retrieve gold-standard context?
```

可以测 retrieval quality。

或者固定 retrieved context，只评价 LLM：

``` text
Fixed Context → LLM → Generated Summary
```

然后测 summary accuracy。

> **Intrinsic = evaluate a particular component.**

------------------------------------------------------------------------

## 7. 为什么 Intrinsic Evaluation 有用？

假设：

``` text
RAG end-to-end accuracy = 55%
```

只看 extrinsic result，你只知道：

``` text
System is not performing well.
```

但不知道哪里出了问题。

Intrinsic evaluation 可以拆成：

``` text
Retriever Recall = 95%
LLM Accuracy     = 58%
```

于是可以判断问题主要出现在 generation component。

------------------------------------------------------------------------

## 8. Intrinsic Evaluation 的重要假设

我们希望：

``` text
Component Metric ↑
        ↓
Whole-system Performance ↑
```

例如：

``` text
Retriever Recall ↑
→ RAG Answer Quality ↑
```

但不一定永远成立。

例如：

``` text
Retrieve more documents
      ↓
Recall ↑
      ↓
More irrelevant context
      ↓
LLM gets distracted
      ↓
Final answer quality ↓
```

所以：

> **Intrinsic metric 改善，不保证 extrinsic performance 一定改善。**

Component interaction 是 evaluation 的重要挑战。

------------------------------------------------------------------------

# 9. 为什么需要 Automatic Evaluation？

课程给出三个主要原因：

``` text
Cost
Scalability
Sufficiency
```

## Cost

Human evaluators 很贵，而且还需要：

-   recruiting
-   training
-   annotation
-   quality control

如果：

``` text
100 models × 10,000 outputs
= 1,000,000 outputs
```

全部人工评价会非常昂贵。

## Scalability

比较很多 systems 时，人类 evaluation 很难 scale。

课程指出，如果进行 pairwise comparisons：

``` text
N systems
→ O(N²) comparisons
```

例如：

``` text
A vs B
A vs C
A vs D
B vs C
B vs D
C vs D
...
```

Automatic evaluation 可以快速重复运行。

## Sufficiency

有些任务答案非常客观，automatic evaluation 已经足够，不需要人类。

# 10. 特别适合 Automatic Evaluation 的任务

## Example 1: Code Generation

模型生成：

``` python
def add(a, b):
    return a + b
```

直接运行：

``` python
assert add(2, 3) == 5
assert add(-1, 1) == 0
```

于是：

``` text
Construct:
Functional Correctness

        ↓

Operationalization:
Run Test Cases

        ↓

Metric:
Pass Rate
```

不需要问人："你觉得代码对不对？"

------------------------------------------------------------------------

## Example 2: Fact-based Questions

``` text
Question:
What is the capital of France?

A. London
B. Paris
C. Berlin
D. Rome

Gold = B
Model = B
```

程序直接：

``` text
prediction == gold
```

然后计算：

``` text
Accuracy = Correct / Total
```

------------------------------------------------------------------------

## Example 3: Math

``` text
Question:
17 × 8 = ?

Gold = 136
Model = 136
```

可以自动判断：

``` text
136 == 136 → Correct
```

因此：

``` text
Construct:
Math Correctness

        ↓

Metric:
Exact-match Accuracy
```

------------------------------------------------------------------------

# 11. 哪些任务比较难自动评价？

例如：

``` text
Write a beautiful short story.
```

Construct 是：

``` text
Beauty / Interestingness
```

但：

``` text
Which story is more beautiful?
```

很难用简单程序判断。

类似：

``` text
Is this response genuinely helpful?
```

也比数学 correctness 难 operationalize。

所以 automatic evaluation 最容易成功的情况是：

> **任务有明确、客观、可验证的标准。**

------------------------------------------------------------------------

# 12. Automatic Evaluation 的最终目标

课程的核心目标：

> **Create a reusable, offline metric that models the construct of
> interest or approximates human labels.**

### Reusable

Metric 做好以后可以反复：

``` text
Model v1
Model v2
Model v3
Model v4
```

### Offline

不需要每次：

``` text
Find humans
→ Annotate
→ Get score
```

而可以：

``` text
Dataset + Metric
→ Run automatically
→ Score
```

### Approximate the Construct

真正目标不是 metric 本身，而是：

``` text
Metric
  ↓
尽可能反映
  ↓
Construct we actually care about
```

------------------------------------------------------------------------

# 13. 一个完整例子：Customer Support LLM

假设我们开发：

``` text
Customer Support AI
```

关心：

``` text
Correctness
Helpfulness
Safety
Response Speed
```

可以 operationalize 成：

``` text
Correctness
→ gold-answer accuracy

Safety
→ toxicity / safety classifier

Response Speed
→ latency in milliseconds

Helpfulness
→ human rating or automatic proxy
```

最后可能得到：

``` text
Accuracy     = 92%
Safety       = 99.8%
Latency      = 420 ms
Helpfulness  = 4.3 / 5
```

一个 system 通常需要多个 metrics，因为：

> **一个 metric 很难代表所有 constructs。**

------------------------------------------------------------------------

# 14. 最重要的 Mental Model

``` text
What do I care about?
        ↓
CONSTRUCT
        ↓
How can I measure it?
        ↓
OPERATIONALIZATION
        ↓
METRIC
        ↓
SCORE
        ↓
Does the score actually reflect
what humans/users care about?
```

真正重要的不是先问：

> "有什么 metric 可以跑？"

而是先问：

> **"我到底想衡量 system 的什么？"**

# 16. Human vs Automatic Evaluation

  Human Evaluation          Automatic Evaluation
  ------------------------- ----------------------------
  人直接判断                Metric / program 自动判断
  能处理复杂 construct      更适合容易量化的 construct
  贵                        便宜
  慢                        快
  难 scale                  容易 scale
  适合 subjective quality   Objective tasks 特别适合
  常用于复杂判断            可重复、offline 运行

# 17. 面试 / 考试答案

## What is automatic evaluation?

> **Automatic evaluation uses a reusable metric or procedure to evaluate
> a system without requiring ongoing human judgments. Ideally, the
> metric operationalizes a construct of interest and correlates with the
> quality we actually care about.**

## What is a construct?

> **A construct is an abstract property we want to evaluate, such as
> correctness, informativeness, toxicity, or text quality.**

大白话：

> **Construct = 我到底想测什么？**

## What does operationalization mean?

> **Operationalization means defining a measurable procedure or metric
> that approximates an abstract construct.**

大白话：

> **Operationalization = 这个抽象东西具体怎么测？**

## Intrinsic vs. Extrinsic evaluation?

> **Intrinsic evaluation measures individual system components, while
> extrinsic evaluation measures end-to-end performance or utility on the
> final task.**

## Why use automatic evaluation?

三个关键词：

``` text
Cost
Scalability
Sufficiency
```

> **Automatic evaluation is cheaper and more scalable than repeated
> human evaluation, and for tasks with objectively verifiable answers,
> such as code execution, factual multiple-choice questions, and math
> problems, automatic metrics may already be sufficient.**

------------------------------------------------------------------------

# 18. 最容易混淆的点

## Construct ≠ Metric

``` text
Construct:
Summary Quality

Metric:
ROUGE
```

不要理解成：

``` text
ROUGE = Quality
```

而是：

``` text
ROUGE attempts to approximate
some aspect of Summary Quality.
```

## Intrinsic 好 ≠ 整个系统一定好

``` text
Retriever metric ↑
```

不保证：

``` text
User utility ↑
```

因为 system components 会互相影响。

## Automatic ≠ 一定比 Human 更准确

Automatic evaluation 的主要优势：

``` text
Cheap
Fast
Repeatable
Scalable
Offline
```

对于复杂、主观 constructs，human evaluation 仍然很重要。


# 20. 和真实 LLM / RAG / Agent Systems 的联系

真实 LLM system evaluation 很少只是：

``` text
Which model has lower loss?
```

更可能同时评价：

``` text
Retriever Quality
Generation Correctness
Hallucination
Safety
Latency
Cost
User Task Success
```

因此设计 evaluation 时，一个重要思维方式是：

> **先定义 construct，再选择能够 operationalize 它的 metric。**

最终目标始终是判断：

> **这个 metric 的改善，是否真的意味着 system 在我们关心的方面变好了？**
